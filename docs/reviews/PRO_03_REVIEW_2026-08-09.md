## Blocking findings

### REWORK-01 — PRO-DATA-03 semantic ambiguity is not fail-closed (P0)

`backend/app/api/import_data.py:20-42` accepts arbitrary `source_type`, `timeframe`, `adjustment_type`, and `timezone` form values. `ImportWorkflowService.preview_import()` stores and classifies those values without validating the supported semantic vocabulary (`backend/app/services/import_workflow_service.py:24-32, 104-133`).

Independent probe against the temporary test database uploaded a valid CSV with `source_type=unknown-provider`, `timeframe=banana`, `adjustment_type=mystery`, and `timezone=Mars/Olympus_Mons`; the API returned HTTP 200 with `can_accept: true`. PRO-DATA-03 requires ambiguous date/timezone/symbol/timeframe/adjustment semantics to block acceptance and leave accepted data unchanged.

### REWORK-02 — Legacy `/api/import/cafef` still auto-mutates without explicit confirmation (P0)

The route previews and immediately calls `ImportWorkflowService.accept_import()` when `preview.can_accept` (`backend/app/api/import_data.py:116-166`). An independent one-request upload returned HTTP 200 and accepted the row. This violates the ExecPlan requirement that every supported entrypoint use the explicit preview → user confirmation → accept contract; preserving a legacy route is allowed only if it enforces that contract or is disabled.

### REWORK-03 — Script entrypoints still expose the old direct mutating importer (P1)

`backend/seed_cafef.py:28` and `backend/scripts/import_batch.py:44` call `CafeFImporter.import_data()` directly. That service remains a last-wins upsert (`backend/app/services/cafef_importer.py:131-154`), bypassing manifests, conflict quarantine, mutation journaling, and guarded rollback. All supported import entrypoints, including scripts, must be routed through the safe workflow or explicitly disabled with an actionable message.

### REWORK-04 — Reviewer fast gate mutated the production DB (P1 process/invariant)

`scripts/verify-v2.ps1` ran Alembic against `backend/sumi.db` instead of an isolated copy. The reviewer measured SHA-256 `4166D749119B0EBB4B9ADF418EA18442FF6E0C14AE762147CD3D0FBE20F76459` before the gate and `47763D8DD068151BD502DC536A4F5C0D3459EF822AEE009A14CA01AE461C241E` after it. A downgrade was run to remove the new tables, but SQLite rewrote the file and the current hash is `F890F5BC16ECE557EA78E19A6095A362DE8641E341382DF66D6A9C997E84F080`; no bit-exact backup was available in the workspace. This violates the repository invariant that tests/UAT must not mutate `backend/sumi.db` and must be resolved before approval.
