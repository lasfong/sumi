### Blocking finding — Bollinger `std` is not an end-to-end contract

`bbands.std` is a released, user-editable registry parameter with range `0.1..10`.  The backend forwards that public key as `std` to the pinned `pandas-ta` implementation.  The installed function instead accepts `lower_std` and `upper_std`; the unknown `std` is swallowed by `**kwargs`, so both `std=2.25` and `std=1.15` silently produce default `BB*_20_2.0_2.0` columns.

REWORK-03's frontend then correctly looks only for names derived from the requested parameter.  Its `toFixed(1)` contract expects `BBU_20_2.2_2.2` for `2.25` (and `1.1` for `1.15`), while the backend returns `BBU_20_2.0_2.0`; it fails closed to no rendered series.  Thus a valid configuration is neither calculated with the selected value nor rendered.  The existing tests and Product UAT use only `std=2.0`, which masks both defects.

Independent read-only reproduction using the project virtual environment:

```text
IndicatorEngine.compute(..., 'bbands', length=20, std=2.25)
=> BBL_20_2.0_2.0, BBM_20_2.0_2.0, BBU_20_2.0_2.0, ...

df.ta.bbands(length=20, lower_std=2.25, upper_std=2.25)
=> BBL_20_2.25_2.25, BBM_20_2.25_2.25, BBU_20_2.25_2.25, ...
```

This violates PRO-IND-01 (registry-driven parameter calculation), PRO-IND-04 (semantic output association), PRO-IND-08 (parity/edge coverage), and PRO-IND-11 (browser-proven released behavior).  Severity: **P1**.
