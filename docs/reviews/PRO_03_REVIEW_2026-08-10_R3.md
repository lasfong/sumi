## REWORK-06 — stale preview must fail closed

`ImportWorkflowService.accept_import()` trusts rows classified as `parsed` at preview time. If another accepted import creates the same candle after preview but before accept, lines 300–337 find that candle and update it with the stale preview values.

Reproduction on SQLite in-memory:

1. Preview a candidate FPT 1D candle dated 2023-10-10 with close `96`.
2. Insert an accepted/current candle for the same key with close `98`.
3. Accept the original preview using its valid `run_id` and `content_sha256`.
4. Actual result: accept returns `accepted` and the current close becomes `96`.

This violates PRO-DATA-03 and PRO-DATA-06, as well as the ExecPlan requirement that stale previews fail closed. A checksum only proves which preview was confirmed; it does not prove that the accepted-data snapshot is still valid.

## Required correction

- Revalidate every staged parsed candidate against the current Candle state inside the accept transaction.
- If any candidate key has changed since preview (including a newly existing candle), reject the entire accept atomically with an actionable stale-preview error; do not create mutations or overwrite data.
- Do not retain the current `UPDATE` fallback for a previewed parsed row unless a future reviewer-approved conflict-resolution contract explicitly permits it.
- Add a deterministic regression test matching the reproduction above and assert the later candle is unchanged, no mutation is written, and the preview has an honest rejected/blocked outcome.
- Rerun focused tests in forward and reverse order, the technical gate, Product UAT, and the full product gate. Retain screenshots/evidence and prove the production database hash is unchanged.
