## Autonomous loop

One orchestrator owns STATE.json and integration. One worker owns the active production batch. Read-only explorers and reviewers may run independently. Reviewers do not concurrently edit worker files; test probes run in their own scratch area. Use native Critic/Challenger/Auditor when available. Role names alone are not independent contexts.

1. Select the earliest dependency-ready task in ROADMAP.md. A blocked branch does not block unrelated tasks. Inspect actual code before assigning scope.
2. Create/update one ExecPlan following PLANS.md: exact allowed files/hunks, protected surfaces, acceptance IDs, contracts/errors, at least one independently derived numerical oracle, rollback of only owned edits, exact isolated verification commands. Reviewer checks consequential semantics/oracles before implementation. Do not make the worker redesign ambiguous business rules.
3. Worker gets a compact task packet: outcome, ExecPlan path, relevant source paths, current findings and stop conditions. Target one coherent capability; split into testable checkpoints internally if too large for Flash. Record checkpoints on disk, not huge chat reports.
4. Worker implements and runs focused tests. Reviewer independently inspects incremental diff against the bootstrap/checkpoint manifest and contracts; challenger tests causal boundaries, malformed data, numeric edges, identity/concurrency and failure paths as relevant. Auditor checks actual outputs, no skipped assertions, no evidence suppression, no unrelated edits and database invariant.
5. Feed actionable findings directly to the worker, not through owner. Up to three repair rounds for the same unresolved issue, each with a fresh focused verification. If still failing: mark blocked with evidence, continue independent tasks; never claim pass or keep an endless fix loop. Stop immediately on destructive-risk escalation.
6. Run full applicable gates once at a stable batch boundary, not after every comment. Required: `./scripts/verify-v2.ps1`; browser gates per AGENTS including `./scripts/run-comprehensive-uat.ps1`; for Replay/Chart/Indicator/Drawing, also `./scripts/run-product-uat.ps1` and inspect retained 1440x1000 screenshots. Preserve machine-readable outputs and exact commands/exit codes. Tests use temporary DB and restored process environment; never import server against production DB. Any code change after gates invalidates affected results and requires rerun.
7. Reviewer seals the exact content digest/manifest, evidence paths and requirement coverage. Mark task accepted only then. Advance automatically. Write concise STATE.json checkpoint after every transition; begin the next worker with fresh context if supported.

## Checkpoint and completion contract

STATE.json is the queue index, not proof by itself. Each task record uses status pending/running/review/accepted/blocked, dependsOn IDs, evidence paths and blocker text. Accepted tasks require a reviewer report identifying actual reviewer context, code digest, tested commands/results, acceptance mapping and limitations. Attach generated logs under ignored scratch/test-results; durable summaries under docs/reviews. Do not hand-edit a pass count to replace running a gate.

On resume validate checkpoint then compare current files to last reviewed manifest. Changed reviewed files invalidate affected acceptance; inherited unrelated changes require reclassification, not deletion. If evidence is missing, verify it rather than trusting prose. Update task statuses and evidence; do not restart completed work merely because chat context is gone.

Final Success Auditor reviews integrated scope, reruns applicable full gates on final code, and writes `docs/reviews/DEV_PROGRAM_FINAL_REVIEW.md` with code/evidence identities, requirements matrix, blocked capabilities and migration handoff. Use `complete` only if every task including bootstrap/final audit is accepted and no mandatory owner/data gates remain. Otherwise use `partial_blocked` (or `paused` for quota/runtime interruption). Never call a fixture-only subsystem production-complete. Final user response: implemented scope, gate result, limitations, next required decision; no copied full logs.
